    AI Agent 评估解密 (Demystifying Evals for AI Agents) #

    📖 文章概述 #

    • 核心主题: AI Agent 评估方法论
    • 目标: 帮助团队更自信地发布 AI Agent
    • 关键洞察: 没有评估 → 被动反应循环；有评估 → 问题在影响用户前可见

    🏗️ 评估的结构 #

    基本定义 #

    • 评估 (Eval): 一种测试
      • 输入 → AI处理 → 评分逻辑 → 衡量成功
      • 聚焦于自动化评估

    评估类型 #

    • 单轮评估
      • Prompt → Response → Grading
    • 多轮评估
      • 随能力进步越来越常见
      • Agent 跨多轮操作，更难评估

    🖼️ 图片分析 1: 简单 vs 复杂评估 # 

    ┌─────────────────────────────────┬─────────────────────────────────────┐
│         简单评估 (Simple)        │        复杂多轮评估 (Complex)       │
├─────────────────────────────────┼─────────────────────────────────────┤
│  Prompt ──► Agent ──► Grader    │  工具 + 任务 + 环境                 │
│                                 │        │                            │
│                                 │        ▼                            │
│                                 │    Agent 循环                       │
│                                 │   (工具调用/推理)                    │
│                                 │        │                            │
│                                 │        ▼                            │
│                                 │   更新环境                          │
│                                 │        │                            │
│                                 │        ▼                            │
│                                 │  单元测试验证                        │
└─────────────────────────────────┴─────────────────────────────────────┘

    要点: Agent 评估复杂因为错误会传播；前沿模型可能找到超越静态评估的创造性方案

    关键术语 #

    术语 定义
    Task 单个测试，含输入和成功标准
    Trial 每次尝试；多次试验产生一致结果
    Grader 评分逻辑，可含多个断言/检查
    Transcript 完整记录(输出/工具调用/推理/交互)
    Outcome 环境中的最终状态
    Evaluation Harness 端到端运行评估的基础设施
    Agent Harness 使模型作为 Agent 行动的系统
    Evaluation Suite 测量特定能力的任务集合

    🎯 为什么要构建评估？ #

    价值主张 #

    • 早期依赖手动测试，但规模化时需要严格评估
    • 区分真实回归与噪音
    • 发布前自动测试
    • 为延迟/成本/错误率提供基线

    案例研究 #

    公司 方法
    Claude Code 反馈 → 简洁性/文件编辑评估 → 复杂行为评估
    Descript 三维度：不破坏/做要求的/做好；演进到 LLM 评分
    Bolt 3个月构建：静态分析 + 浏览器Agent + LLM裁判

    🔬 如何评估 AI Agent #

    评分器类型 #

    1️⃣ 基于代码的评分器 # 

    方法:
├── 字符串匹配
├── 二元测试 (Pass/Fail)
├── 静态分析
├── 结果验证
└── 工具调用验证

优点: 快速、便宜、客观、可复现
缺点: 对有效变化脆弱、缺乏细微差别

    2️⃣ 基于模型的评分器 # 

    方法:
├── 基于Rubric的评分
├── 自然语言断言
└── 成对比较

优点: 灵活、可扩展、捕捉细微差别、处理开放式任务
缺点: 非确定性、昂贵、需要校准

    3️⃣ 人类评分器 # 

    方法:
├── 领域专家审查
├── 众包判断
└── 抽样检查

优点: 黄金标准、匹配专家判断
缺点: 昂贵、缓慢

    评估类型对比 #

    类型 目的 目标
    能力评估 Agent能做好什么？ 从低开始，针对困难点
    回归评估 还能处理旧任务吗？ ~100% 通过率

    进阶策略: 高通过率的能力评估可"毕业"到回归套件

    按Agent类型评估 #

    🖥️ 编码Agent # 

    评估要素:
├── 明确定义的任务
├── 稳定的环境
└── 全面的测试

基准测试:
├── SWE-bench Verified (修复GitHub Issues)
└── Terminal-Bench (端到端技术任务)

策略:
├── 确定性评分器 → 验证结果(单元测试)
└── Transcript评分 → 验证行为(工具使用/代码质量)

    💬 对话Agent # 

    挑战: 交互质量重要；常需第二个LLM模拟用户

成功维度:
├── 状态检查 (票务解决)
├── Transcript约束 (<10轮)
└── 语气 (LLM Rubric)

基准测试:
├── τ-Bench
└── τ2-Bench (模拟多轮交互 + 用户画像)

    🔍 研究Agent # 

    挑战: 主观质量、变化的事实依据、长输出

策略:
├── 组合多种评分器
├── 接地检查 (来源支持声明)
├── 覆盖检查 (包含关键事实)
└── 来源质量检查

基准测试: BrowseComp (在信息海洋中找针)

    🖱️ 计算机使用Agent # 

    特点: 通过GUI交互(截图/点击)；需真实/沙盒环境

基准测试:
├── WebArena (浏览器任务)
└── OSWorld (操作系统控制)

权衡:
├── DOM-based: 快速，高token
└── 截图-based: 慢，token高效

    🖼️ 图片分析 3: pass@k vs pass^k # 

    成功率
  │
100% ┤ ╲
     │   ╲  pass@k (至少一次成功)
     │     ╲
     │       ╲
 50% ┤─────────╲────────────
     │         ╱
     │       ╱  
     │     ╱    pass^k (全部成功)
     │   ╱
  0% ┤ ╱
     └─────────────────────► k (试验次数)
     
关键洞察: k=10时，两者讲述相反的故事
    • pass@k: k次尝试中至少一次正确的概率
      • 适用于"一次成功就够"的场景
    • pass^k: 所有k次试验都成功的概率
      • 适用于"一致性关键"的场景

    🗺️ 从零到一：路线图 #

    阶段一：收集任务 # 

    Step 0: 尽早开始
  └── 20-50个简单任务 + 真实失败案例

Step 1: 使用手动检查
  └── 将Bug追踪器/支持队列转化为测试用例

Step 2: 明确任务
  └── 两位专家应对通过/失败达成一致
  └── 创建参考解决方案证明可解
  └── 0% pass@100 通常意味着任务有问题

Step 3: 平衡集合
  └── 测试应该发生和不应该发生的地方
  └── 避免类别不平衡

    阶段二：设计Harness和评分器 # 

    Step 4: 健壮Harness
  └── 隔离试验(干净环境)
  └── 防止共享状态导致相关失败

Step 5: 深思熟虑的评分器
  ├── 优先确定性评分器
  ├── 必要时使用LLM/人类
  ├── 评分结果，而非死板路径
  ├── 允许部分得分
  ├── 用人类校准LLM裁判
  └── 防止作弊/绕过

    阶段三：长期维护 # 

    Step 6: 检查Transcript
  └── 验证失败是真正的Agent错误，而非评分器错误

Step 7: 监控饱和度
  └── 100%分数无法提供改进信号
  └── 随模型改进修订评估

Step 8: 开放贡献
  └── 将评估视为活的工件
  └── 让产品/客户团队贡献任务
  └── 实践评估驱动开发

    各方法对比表 #

    方法 优点 缺点
    自动化评估 快速、可复现、无用户影响、可扩展 前期投入、需维护、可能遗漏真实模式
    生产监控 真实用户行为、捕捉合成遗漏 反应性、嘈杂、缺事实依据
    A/B测试 测量实际结果、控制混杂因素 慢、需流量、不理解原因
    用户反馈 预期惊喜、与目标相关 稀疏、偏向严重问题、不自动
    手动Transcript审查 建立直觉、捕捉细微问题 耗时、不可扩展、定性
    系统化人类研究 黄金标准、处理主观性 昂贵、缓慢、评估者分歧

    LangSmith 追踪、数据集管理、LangChain集成
    Langfuse 自托管开源替代方案
    Arize Phoenix(追踪/调试) + AX(SaaS监控)

    建议: 选择适合工作流的框架，但将精力投入到高质量测试用例和评分器上
